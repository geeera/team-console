# 0003 — The console's GitHub identity: a GitHub App per environment, owner writes on the owner's own token

Status: accepted (owner decision in chat, 2026-09-29, recorded on #21 and #25: «и GitHub App тоже включай»; the
technical shape below is a team decision under `reference/decision-policy.md`). Date: 2026-09-29, reworked the
same day after the PR #57 reviews. Amends [ADR 0001](0001-stack-and-architecture.md) decisions 6, 8, 10, 14 and
20. Facts marked "verified" were read from GitHub's documentation on this date. Decisions 1 and 8 amended on
2026-10-05 by #62 (owner decision in chat: «Первый вариант, через метку для тестовых задач»). Decisions 2(a) and 6
amended on 2026-10-05 by #194 (architect note; a team decision under `reference/decision-policy.md`): one
installation-wide, `metadata: read`-only token for listing the installation's repositories.

## Context

ADR 0001 decision 6 gave the `api` Worker a fine-grained personal access token (PAT) of the owner's account, and
the #9 threat model split it in two (a repo-only PAT for dev/stage, an all-product PAT for production, both as the
Worker secret `GITHUB_TOKEN`). The owner replaced that with "a GitHub App for the console" once the product-team
plugin 0.10.0 moved the agents onto GitHub Apps of their own (`reference/identities.md`).

That plugin change is what makes this decision non-trivial. Since 0.10.0 an owner command (`/approve`, `/go`,
`done`, `/reject why`) **counts only when the comment's author is the owner's login** (`ptlib/commands.parse`, the
demo decisions block, reversals of team decisions). A comment written with a GitHub App *installation* token is
authored by `<app-slug>[bot]`, so an answer the console posted that way would render correctly and be ignored by
the team. The plugin's own team chat has the same problem and solves it by refusing to post an owner answer with
anything but a token of the owner's account (`PT_OWNER_TOKEN`, `gh.owner_token`). The console must land on the
same side of that line. The plugin's definition of "the owner" is the repository's owner (`GET /repos/{repo}` →
`owner.login`, `gh.owner_login`), not a configured name.

Facts that shape the decision (verified 2026-09-29):

- A GitHub App has **one installation per account**, with one repository selection. "Install the same app on
  `team-console` for dev/stage and on all product repos for production" is therefore not expressible with one
  app — the split ADR 0001 / #9 wanted needs separate apps.
- An app has **one webhook URL and one webhook secret**, and receives events for every repository it is
  installed on; payloads carry `installation.id`. `issues`/`issue_comment` need Issues read, `pull_request`
  needs Pull requests read, `workflow_run` needs Actions read, `release` and `push` need Contents read;
  `installation_repositories` arrives without any permission.
- Installation access tokens live one hour, are minted with a JWT (RS256, `exp` at most 10 minutes) signed by
  the app's private key, and the mint request may **downscope** the token to named repositories and to a subset
  of the app's permissions. **Downscoping is chosen by the caller**: whoever holds the private key can mint a
  token with the app's full permissions on every installed repository. Rate limit: 5,000 requests/hour per
  installation — a budget separate from the owner's account and from the agents' team app.
- **User access tokens** (`ghu_…`, "user-to-server") are minted by the same app through the OAuth web flow
  (PKCE supported) and attribute every write to the user. With "Expire user authorization tokens" on, they live
  8 hours and come with a single-use refresh token (`ghr_…`) valid 6 months; a refresh returns a new pair, and
  **the old access token and refresh token stop working at once**. Whoever keeps refreshing keeps the grant
  alive indefinitely; only a revocation ends it. Errors of the token endpoint are reported in the JSON `error`
  field (e.g. `bad_refresh_token`), not reliably by the HTTP status. Their reach is the intersection of the
  app's permissions and installation with the user's own access; their rate limit is the user's.
- The **App Manifest flow** (`POST https://github.com/settings/apps/new` with a manifest, then
  `POST /app-manifests/{code}/conversions` within one hour) creates an app with prefilled permissions, events,
  callback and webhook URL and returns `id`, `client_id`, `client_secret`, `webhook_secret` and `pem` in one
  response — the owner only presses "Create GitHub App".
- `DELETE /applications/{client_id}/grant` (Basic auth `client_id:client_secret`, body `access_token`) revokes
  the app's grant for that user and every token of it; "Revoke all user tokens" in the app's settings does the
  same for everyone.
- The `api` Worker sits behind Cloudflare Access (ADR 0001 decision 7, #8): only the owner reaches any
  `/api/*` route, including an OAuth callback; #8's CSRF middleware refuses every non-GET request that is not
  same-origin JSON. The `hooks` Worker is public and holds no GitHub credential (#12 threat row 6).

| 2 | **Amended by #194 (2026-10-05):** reads of *repository content* stay per repository as written below. One read is not about a repository but about the installation itself — Settings › Projects listing the repositories the `team-console-<env>` installation can see (`GET /installation/repositories`) — and a per-repository token cannot answer it. That one read uses a **second token shape: installation-wide, downscoped at mint to `metadata: read` only** (no `repositories` member in the mint body, no other permission). `metadata: read` is the narrowest permission a token can carry, **but it is not "names only"**: GitHub answers it (verified against "Permissions required for GitHub Apps", 2026-10-05) with the full repository object, collaborators and their permission levels, commit comment bodies, events, contributors, tags, topics, rulesets, custom properties, stats and forks — and without a `repositories` member the token covers **every** repository the installation can see, private and unregistered ones included. No issues, no contents, no actions, but breadth across repositories. Therefore the token is used for **`GET /installation/repositories` only**, and that is enforced in code, not by convention (decision 6 as amended: a distinct source kind that the generic client refuses). It is minted for the installation found from the **connected owner account** (decision 3/4: `account.id` of the installation equals the pinned `user_id`; `GET /app/installations` with the JWT, never a configured login), cached per isolate apart from the per-repository tokens, never persisted, logged or returned. Rejected: minting the installation-wide token with the full read-only set of (a) — one token that reads every repository's issues and contents is a bigger thing to hold in memory for no gain; listing through the owner's user token — the owner's rate limit and a refreshable credential for a read, the very split this decision avoids; `GET /users/{login}/installation` — ties the lookup to a login string (#106) and breaks on a rename, where the pinned id does not. **Two kinds of tokens, split by who is speaking.** (a) **Reads** — issues, PRs, workflow runs, Contents (`project.yml`, `decisions_dir`), releases, milestones, and the Settings screen's "can the console read this repo" check — use **installation tokens**, minted per repository and **downscoped at mint to read-only** (`metadata`, `issues`, `pull_requests`, `contents`, `actions`: read). (b) **Everything the owner says** — answers and commands (`/approve`, `/reject`, `/go`, `/no-go`, `/override`, `done`, #10), PM chat messages (`<!-- pt-chat:owner -->`, #17/#26), pause/resume and the other team commands (#29) — is written with a **user access token of the owner's account** obtained from the same app (decision 3). The console never writes to GitHub as `<slug>[bot]`. **Before every owner write, and when a product is registered**, the Worker requires the repository's `owner.login` to equal the connected login (case-insensitive) and `owner.id` to equal the numeric user id pinned at connect; otherwise **409 `github-owner-mismatch`** — the console refuses the way `gh.owner_token` refuses, instead of posting an answer the team would ignore. **The trade-off stated honestly**: the app must hold **Issues: write** (user tokens are capped at the app's permissions), so its private key is *not* a read-only credential — a holder can mint a full-permission token and act as `team-console-<env>[bot]` on every installed repository: change labels (`team:paused`, `status:*`, `needs:owner`, `design:*`), close issues, rewrite issue bodies the agents read as tasks, and edit existing comments (#60). The read-only downscope protects the token that exists in memory on every request, not the key. We accept this over the alternative of a read-only app plus an owner PAT for writes, because that PAT would itself be an **owner-grade** write credential (its comments *are* owner commands; bot writes are visible as the bot and, #60 aside, never count as the owner), with a manual repository list, a yearly expiry and no app-side revocation. The residual risk is bounded by decisions 6–8: the production key lives only in the production `api` Worker, is deleted from the app in the incident runbook, and every bot write is attributable. | Attribution is the whole point: the plugin counts owner commands only from the owner's login, and the console must not ask the plugin to trust a bot as the owner's proxy (see "Alternatives" below). Plugin impact of the chosen option: **none**, with one caveat — the plugin's rule checks the comment's author and reads its *current* body, so any Issues-write holder (the team and review apps today, the console apps now) could edit an old owner comment into a command; that is a plugin finding, tracked as #60, and holds regardless of which option the console takes. | (a) Everything on the user token: reads would then hang on a refreshable credential the owner can revoke or let lapse (6 months idle), and share the owner's 5,000/hour with the plugin's team-chat session and their own `gh`; no per-installation budget. (b) Owner writes on a fine-grained PAT stored as a Worker secret (`OWNER_GITHUB_TOKEN`, the plugin's `PT_OWNER_TOKEN` shape): lets the app stay read-only (a leaked key would be a pure read leak) but puts a standing owner-grade write credential in the Worker instead, with its own expiry (1 year), a repository list the owner must edit by hand on every new product, and one more secret per environment. Kept as the documented fallback if #59 cannot ship in the first sprint (`OwnerTokenSource` is an interface — the secret-backed implementation is ten lines), never as the target. (c) **A plugin change that trusts a console bot as an owner proxy**: rejected outright — it would reopen the hole 0.10.0 closed. `commands.parse` would accept a second login; any process with the console's private key could then `/go` a release on every product the app is installed on, and the agents' `same_account` heuristic would have to learn a bot that "is" the owner. |

| 4 | **Storage and refresh of the user token pair.** D1 table `owner_connections` (migration **`0005_owner_connections.sql`**, reserved for #59): `environment` (PK), `login`, `user_id INTEGER`, `access_token_enc`, `refresh_token_enc`, `access_expires_at`, `refresh_expires_at`, `key_id`, `version INTEGER`, `refreshing_until INTEGER NULL`, `connected_at`, `updated_at`. **Keys**: the Worker secret `TOKEN_ENCRYPTION_KEY` (32 random bytes, base64) is never used directly; **HKDF-SHA256** derives two subkeys (`info` = `owner-token-v1` and `oauth-state-v1`, salt = environment); each token is **AES-256-GCM** encrypted with a fresh 12-byte IV, AAD = `environment:column`; `key_id` = first 8 hex of SHA-256 of the master key. **Decrypt failure or `key_id` mismatch** (the key was rotated without disconnecting first, or the row is corrupt) → the row is deleted, a security warning logged, and the request answers **403 `github-owner-not-connected`** — never a 500. **Refresh is single-flight**: on use with < 30 minutes left, the isolate takes a D1 lease — `UPDATE owner_connections SET refreshing_until = :now+60 WHERE environment = :env AND version = :v AND (refreshing_until IS NULL OR refreshing_until < :now)` — and only the lease holder calls `grant_type=refresh_token`; everyone else waits (≤ 5 × 200 ms) and re-reads. Success → write the new pair `WHERE version = :v`, `version + 1`, lease cleared; the response is decided from the JSON `error` field — `bad_refresh_token` (or any `error` naming the grant) → delete `WHERE version = :v`, then 403 `github-owner-not-connected`; a transport/5xx failure or a D1 write failure after GitHub rotated the pair → lease expires, the next caller re-reads and refreshes again from the stored pair, and if that one is `bad_refresh_token` the chain is gone → delete → 403. On a **401 from an API write** the caller re-reads the row and refreshes once before giving up. No cron. The **403 problem carries an extension member `connectUrl`** (`/api/v1/github/connect`) — not `instance`, which RFC 9457 reserves for the occurrence — and the client branches on the problem `type`. **An unexpected `github-owner-not-connected` is a security signal** (someone else refreshed the chain): logged as such, shown in Settings, and the runbook in decision 7 applies. ## Alternatives considered for the attribution problem, in one place

| Option | Verdict |
| ------ | ------- |
| (a) All console traffic on a user access token | Rejected for reads (decision 2); **chosen for owner writes**. |
| (b) Owner writes on a fine-grained PAT secret, installation token for the rest | Same attribution outcome with less code and a read-only app; loses on the asset it introduces (an owner-grade write credential at rest) and on operations (manual repo list, yearly expiry). Fallback only. |

## Owner procedure (replaces the PAT and per-repo webhook steps of the checklist; #61 ships it)

1. After the first deploy of an environment (#25) — the Worker hostnames must exist — run `tools/owner-setup/create-apps.sh --env <env>` (#61, on the owner's machine after `gh auth login` and `npx wrangler login`). It opens the **App Manifest** page for `team-console-<env>` with everything prefilled: homepage `https://github.com/geeera/team-console`; callback `https://team-console-<env>.<account>.workers.dev/api/v1/github/callback`; webhook active at `https://team-console-hooks-<env>.<account>.workers.dev/hooks/github`; permissions `metadata: read, issues: write, pull_requests: read, contents: read, actions: read`; events `issues, issue_comment, pull_request, workflow_run, release, push`; `public: false` ("Only on this account"); "Expire user authorization tokens" on, OAuth-during-installation off, Device Flow off. The owner presses **Create GitHub App**.
2. GitHub redirects to the script's localhost listener with a one-hour `code`; the script converts it and receives `id`, `client_id`, `client_secret`, `webhook_secret`, `pem`. It pipes — never printing, never writing to disk, never on argv — `pem` (converted to PKCS#8) → `api` secret `GITHUB_APP_PRIVATE_KEY`; `client_secret` → `api` secret `GITHUB_APP_CLIENT_SECRET`; `webhook_secret` → `hooks` secret `WEBHOOK_SECRET`; a fresh `openssl rand -base64 32` → `api` secret `TOKEN_ENCRYPTION_KEY`; and `id`, `client_id` and the owner login → GitHub Environment variables `CONSOLE_GITHUB_APP_ID`, `CONSOLE_GITHUB_APP_CLIENT_ID`, `OWNER_GITHUB_LOGIN` (the first two are named `CONSOLE_*` on the GitHub side only — decision 7 — `deploy.yml` still hands the Worker plain `GITHUB_APP_ID`/`GITHUB_APP_CLIENT_ID`).
3. The script opens the app's **Install** page; the owner chooses **Only select repositories** — `dev` and `stage`: only `geeera/team-console`; `production`: the product repositories. Deliveries 404 until #12 is deployed; GitHub keeps them redeliverable.
4. Redeploy the environment (the variables reach the Worker on the next deploy).
5. Once #59 is deployed: open the console → Settings → **Connect GitHub** → authorize as the owner. Needed in **every environment that is expected to write**: production (real answers), **stage** (the Playwright e2e of #14 answers on the sandbox product through the service identity, which #10 accepts only outside production and, since #62, only on issues labelled `e2e:fixture` that are not a release, a design or a team question — the owner creates that label on `geeera/team-console` before such a run), and dev if the owner answers from it; reads work without it.
6. Repeat 1–5 per environment. Registering a further product later = add it to the production app's installation + Settings row + routine token; no webhook, no token list.
