# 0001 — Stack and architecture

Status: accepted (team decision under `reference/decision-policy.md`; the owner reverses any row with `/reject why`).
Date: 2026-09-29. Facts marked "verified" were read from the vendor's documentation on this date.

## Context

Team Console is a single-user control panel for the product-team plugin (see `docs/product-brief.md`): questions
answered in one tap, chat with the PM, a sprint board, designs and the demo page — on iPhone and Mac equally, as
a PWA first, with push notifications. GitHub is the source of truth; the app keeps no data of its own beyond what
push and the chat need. Budget is $0, the repository is public, and the owner already decided: PWA first (native
SwiftUI later on the same backend), PM chat answered by a Claude Code routine woken per message on the owner's
subscription (no paid Claude API), one user.

Constraints that shape everything below:

- Every comment the app writes is the owner's own (same GitHub account the agents use). It must be one line,
  typed by item and quote the owner's words — exactly what `backlog answer` writes — so the team's parsers
  (`scripts/ptlib/commands.py`, `brief.py`) read it without a second grammar.
- The token that lets the app read and write issues can `/approve` designs, `/go` a release and comment on any
  product repo. Whoever reaches the API acts as the owner. Authentication is therefore the first architectural
  concern, not a feature.
- GitHub does not notify the owner about comments written by the owner's own account, so "something needs you"
  has to come from webhooks, not from GitHub notifications.
- Claude Code routines (verified): triggers are schedule (minimum interval one hour), API (`POST
  …/routines/{id}/fire` with a per-routine bearer token, 30 fires/hour per routine, 100/hour per account, plus a
  daily run cap per account) and GitHub events limited to `pull_request` and `release`. There is **no
  `issue_comment` trigger**, so a chat message cannot wake a routine directly; something must call `/fire`.
- iOS web push (verified, WebKit 16.4 announcement): works only for web apps added to the Home Screen with
  `display: standalone|fullscreen`, permission must be requested from a user gesture, standard Push API +
  VAPID, no Apple Developer Program needed. Declarative Web Push (iOS 18.4+) is optional and backward compatible.
- Cloudflare Access (verified): can protect a Worker's production `workers.dev` URL; on Pages it protects only
  preview deployments, not the production `*.pages.dev` hostname. The owner has no custom domain (none assumed).
- Projects are spaces (brief, 2026-09-29): many products, each with its own chat history, questions, board,
  artifacts grouped by type and searchable, and settings; above them a cross-project "Needs you" list and an
  overview. "No database of our own" still holds: every artifact must be discoverable from the product
  repository by the plugin's own conventions (`decisions_dir` in `.product-team/project.yml`, `team:demo`,
  `team:run-log`, `team:paused`, `design:*` labels, `docs/design/directions/`, GitHub Releases, `CHANGELOG.md`).

## Consequences

- (Amended by [ADR 0003](0003-console-github-app.md): the fine-grained PAT and the per-repo webhooks below are
  replaced by three GitHub Apps, one per environment.) Owner setup before the first deploy (all `access`, no money): Cloudflare account + Zero Trust team (free), the
  `workers.dev` subdomain, an API token for Actions, Access applications for the three app Workers (OTP to the
  owner's email; optional GitHub IdP), one service token for stage e2e; a fine-grained PAT (decision 6); a
  webhook per product repository pointing at the `hooks` Worker with a shared secret; one routine per product
  with an API trigger token. All go into GitHub Environments / `wrangler secret`; the checklist lists them.
- The plugin needs the `pm-chat` routine skill and chat markers (decision 12) before chat is useful. Questions,
  board, designs and demo work without any plugin change.
- Push works only after the app is installed to the Home Screen on iPhone; the app must teach this on first
  run. Mac (Safari and Chrome) gets push from the installed app or the browser directly.
- The Access session expires (24 h by default): API calls then receive a redirect to the login page. The client
  detects this (a redirect, the Access login host, or our own `access-missing`/`access-unverified` problem; a
  non-JSON body is only conclusive on a 401, since a non-Access 403 — a Cloudflare WAF or rate-limit page — would
  otherwise be mistaken for an expired session) and shows a «Сессия истекла» screen with a manual sign-in button
  instead of reloading automatically or showing a parsing error.
- Two Workers per environment, six in total, plus one Pages project for Storybook: well inside the 100 Workers
  and 100 Pages projects free limits.
- The native client later authenticates against the same Access-protected API; the concrete method (Access
  login in a web view yielding the JWT, or a service token per device) is decided in its own record.
- Deviation from the deploy recipe's default (Pages for the SPA) is intentional and recorded in decision 4.

## Free-tier limits to watch

| Service | Limit (verified 2026-09-29) | Where it bites |
| ------- | --------------------------- | -------------- |
| Cloudflare Workers Free | 100,000 requests/day; 10 ms CPU per request; 50 subrequests per request; 5 Cron Triggers; 100 Workers | Push fan-out encrypts one payload per subscription: 2–3 devices fit in 10 ms; measure before adding devices. Board endpoints must aggregate GitHub calls under 50 subrequests. |
| Cloudflare D1 Free | 5 M rows read/day; 100,000 rows written/day; 5 GB | Webhook dedupe rows — fine for a few thousand events/day. |
| Cloudflare Pages Free | 500 builds/month; 20,000 files; 25 MiB per file | Storybook uses direct upload, so no builds are consumed. |
| Cloudflare Zero Trust Free | 50 users; Access, OTP and IdP logins included | One user. Never add a second user without checking the plan. |
| GitHub REST API | 5,000 requests/hour per app installation for reads and the owner's own 5,000/hour for owner writes (ADR 0003; was "per PAT"); secondary limits on bursts of writes | Cache reads for 30–60 s in the Workers Cache API; the board is read-heavy. |
| GitHub Actions | Free for public repositories on standard runners | Keep `concurrency`/`cancel-in-progress`; no cron workflows. |
| Claude Code routines | 30 fires/hour per routine, 100/hour per account, daily run cap per account; draws the subscription quota | Every chat message is a session: the routine must batch and exit early; the console shows "PM will answer in a few minutes" and the fire result. `Retry-After` honoured. |
| Apple Push (web) | No quota published; subscriptions may be dropped when the app is removed | Prune subscriptions on 404/410 from the push endpoint. |
