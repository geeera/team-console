# 0008 — Multi-tenant console and where jobs run

Status: accepted (owner direction in chat, 2026-11-09: the console becomes a paid multi-tenant product; two
execution modes — a customer-installed runner or a hosted runner on the customer's own Anthropic API key; the
owner's team follows the same rules as any customer and depends on no particular machine; billing is designed as a
seam only. The owner accepted every recommendation of "Owner decisions" below on 2026-11-09 in the team chat,
recorded on #446. Everything below that is not one of those decisions is a team decision under
`reference/decision-policy.md`, reversible with `/reject why`). Date: 2026-11-09, revised the same day after the QA
and SECURITY reviews of PR #460 (an `actions-ephemeral` backend; the delivery plan inside the ADR; deny-by-default
route scope; the GitHub Actions packaging's auth and secret design; hosted network isolation and key handling; the
spend cap as reservation; the runner's pinned trust root; sign-in, setup-URL and invite flows; the sealing
envelope; a first-customer security gate; slug enumeration accepted). Phase 2 of #309 (umbrella #446; the
architect notes of 2026-11-09 on #446 are superseded by this ADR where they differ). Amends
[ADR 0006](0006-console-source-of-truth.md) decisions 1, 6, 8, 10 and 11 and its "Runner and job queue"; the
single-owner model of [ADR 0001](0001-stack-and-architecture.md) decision 7 (Cloudflare Access as the only door)
and [ADR 0003](0003-console-github-app.md) decisions 3–4 (one owner connection per environment). Number 0007 is
held by #386. Threat model: `docs/security/309-threat-model.md`, components C9–C11 added with this ADR.

## Context

ADR 0006 made the console the tracker for one owner and one team, with jobs on the owner's Mac under the owner's
Claude subscription. Two things changed on 2026-11-09:

- **The product.** The console is to be sold to other teams. Every table, route and credential the console has is
  single-tenant today: `projects` has no owner, `owner_connections` is one row per environment, the owner is
  `OWNER_EMAIL` behind Cloudflare Access, the GitHub App installation is "the" installation, and the route matrix
  (#449) knows `owner` and `job` but no account. Retrofitting a tenant boundary after the team-console import and
  after the first customer would mean migrating live rows twice; doing it now means migrating one owner's fixtures.
- **Where Claude runs.** Anthropic's terms for Claude Code (`code.claude.com/docs/en/legal-and-compliance`,
  "Authentication and credential use" and "Can customers offer Claude Code in their products?", read 2026-11-09)
  say: third-party developers may not offer Claude.ai login in their applications, may not route requests through
  Free/Pro/Max/Ultra plan credentials on behalf of their users, and may not collect, store or intermediate Claude.ai
  credentials or session tokens — sign-in must complete through Anthropic's own flow; products that run Claude Code
  must run the unmodified binary, and each end user authenticates with their own API key, subscription or
  third-party-provider credential, billed to them. The Agent SDK overview repeats it: "Anthropic does not allow
  third party developers to offer claude.ai login or rate limits for their products". So a hosted runner may use a
  customer's **API key**, never a customer's subscription; a runner on the customer's own machine may run the
  unmodified CLI however the customer signs in there. The owner adds a rule stricter than the terms: **no path ever
  uses a Claude.ai subscription on our servers**, and the owner's own team gets no special local-Mac path — the
  late-October cloud failure ("organization has disabled Claude subscription access for Claude Code") showed what a
  dependency on one machine or one login costs.

Constraints that stay: $0 until the owner approves spend (Workers Free, D1 Free, Zero Trust Free; the repository is
public); agents never see a secret value other than their own job token (and, inside a job, the inference
credential the job runs on); item text, comments, PR bodies, CI logs and imported content are data, never
instructions; the team-console cutover (#437, Phase 6) must not wait for the whole product to exist.

## Decisions

| #   | Decision | Why | Rejected |

| 1 | **Accounts are the tenant.** `accounts` (ULID `id`, `slug`, `name`, `plan`, `entitlements` JSON, timestamps) own `projects` (`+ account_id NOT NULL`), `runners`, `role_keys`, `jobs`, `installations`, `inference_keys` and `audit_events`; every other tracker table stays keyed by `project_slug` and is reached only through its project. `projects.slug` stays **globally unique** (first come, like a package name), so every existing URL, DTO and route keeps its shape and the plugin's `TC_PROJECT` stays a slug. **Accepted consequence:** a create conflict on a taken slug tells an account that some other account holds it — a slug is an enumeration oracle, like a package or user name, and is treated as public; nothing *behind* a slug is enumerable (decision 2). **System slugs are reserved** (`admin`, `api`, `owner`, `settings`, `needs-you`, `overview`, `github`, `hooks`, `runner`, `accounts`, `p`, `a`, `t`, and every top-level route segment of the console and the API) and refused on create. The migration creates one account for the existing owner (`slug = 'owner'`) and attaches every existing project, connection, installation, runner and job to it; existing routes are unchanged by it. | One foreign key on the handful of account-level tables and a single chokepoint for the rest is less surface than `account_id` on 20 tables; a globally unique slug avoids re-shaping every route and the plugin's client while nothing customer-facing exists yet. | `account_id` denormalised onto every table (a 20-table migration now, before the shape is proven — revisit if the chokepoint test finds a leak); per-account URLs `/a/:account/p/:slug` (changes the plugin's addressing before cutover; would also remove the oracle — reconsider if customers object); one D1 per tenant (Workers bindings are static; the D1 HTTP API would need an API token in the Worker). |
| 2 | **Isolation is deny-by-default: every registered route declares its scope rule, and one chokepoint applies it.** Scope rules: `project` (through `projects/lookup.ts` with the request's scope), `account` (owner-of-account on `/api/v1/accounts/:id/*`), `own-user` (sessions, the user's own connection, push subscriptions), `operator` (`/api/v1/admin/*`, Access JWT + operator allowlist), `runner` (`/api/v1/runner/*`), `public` (`/healthz`, `/environment`, the brand icons). **Scopes:** a `user` = its memberships; a **`job` = its own project only** (`project_slug` of the job — never the whole account, so a job of P1 cannot touch P2, R4 as in ADR 0006); a **`runner` = its `allowed_projects`**; `operator` = plans and entitlements, never project rows. `projects/lookup.ts` takes the scope and answers 404 `project-not-found` for any project outside it — the same answer as a slug that does not exist. The **route inventory spec** walks every route registered on the Hono app (`app.routes`) — `/projects/*`, `/needs-you`, `/overview`, `/github/*`, `/push`, `/environment`, `/accounts/*`, `/jobs/*`, `/runner/*`, `/auth/*`, `/invites/*`, `/admin/*` and anything added later — and **fails on a route without a declared scope rule**; `/needs-you` and `/overview` list the scope's projects only; repos never take a `project_slug` or `account_id` from a body, only from the admitted project or account. **Webhooks** (`hooks` Worker): a delivery reaches a project only when the delivery's installation is linked to the project's account (`installations.account_id = projects.account_id`) **and** the repository matches by **id** (`projects.repo_id`, added in the account migration), never by `full_name` — a rename or transfer cannot land on another account's project. A two-account e2e covers webhooks, push, overview, needs-you and the GitHub routes. | The #449 matrix proved that a table in code plus an inventory test holds better than per-handler checks; deny-by-default is what makes "the matrix becomes account-scoped" verifiable rather than hoped. | Row-level checks in every repo (40 places to get wrong); an allow-list spec over two prefixes only (the first revision of this ADR — it left `/needs-you`, `/overview`, `/github/*`, `/push` and the coming routes unchecked); a separate Worker per tenant (not free). |
| 3 | **Sign-in is "Sign in with GitHub" through the environment's existing GitHub App; sessions are the console's own; every state-changing step is a POST guarded as a write.** `users` (`id`, `provider`, `provider_user_id`, `login`, `email`, `avatar_url`), `sessions` (opaque 256-bit id hashed in D1; cookie **`__Host-tc_session`**, `Path=/; Secure; HttpOnly; SameSite=Lax`; 24 h idle / 30 d absolute; rotated on sign-in; revocable per user), `account_members` (`account_id`, `user_id`, `role ∈ owner \| member`, `invited_by`, `joined_at`), `invites`. **OAuth**: `state` is random, single-use, 10 minutes, bound to a `__Host-tc_preauth` cookie set at `/auth/github/start`, with **PKCE**; the callback is a GET that only completes the exchange and then **POSTs nothing on the user's behalf** — the session is created only when `state`, the pre-auth cookie and the PKCE verifier agree (login CSRF and session swapping fail). The first sign-in with no membership creates an account with that user as owner (self-service, rate-limited per user and per IP). **Access ↔ GitHub identity**: the owner's Access identity is linked to the owner's GitHub user row **only while the owner is signed in through both doors in one session** (an explicit "link" POST); never by email equality. `OWNER_EMAIL` and Access retire from `/api/*` at the first customer; Cloudflare Access stays in front of **operator** routes (`/api/v1/admin/*`), where **the Worker itself verifies the Access JWT and an operator allowlist** — a session cookie never satisfies it — and, as today, as a perimeter on dev/stage. `csrfMiddleware` exempts bearer identities `runner` and `job` and nothing else. **The GitHub App manifest is `public: false` today (ADR 0003); flipping it public so customers can install it is the moment every control in this row, in decision 4 and in the invite rules must already be live** (the first-customer gate, decision 11). `identity.kind = 'user'` carries `userId` and the membership list; "the owner" in every ADR 0006 rule means **an `owner` member of the project's account**. GitLab sign-in arrives with Phase 5 on the same `users` table. | The customers are GitHub users and the OAuth app already exists (ADR 0003's user-to-server flow); no new identity vendor, no email/password to protect; roles stay the two the decision policy knows (owner decides, member works). | Cloudflare Access per customer (no self-service, 50 seats, operator-configured); Auth0/Clerk/WorkOS (a vendor and a free-tier ceiling for a feature GitHub OAuth gives); magic-link email (needs an email provider now — invites are links shown to the inviter instead). |
| 4 | **Installations and owner-grade connections are per account.** `installations` (`account_id`, `provider`, `installation_id`, `account_login`, `linked_by_user_id`, `linked_at`, `suspended_at`) replaces the environment-wide "project installation" (0006 migration): the GitHub App's **setup URL** receives `installation_id` + a `state` that is **signed, bound to the current session, single-use and short-lived**; the console verifies through the **user's own token** (`GET /user/installations`) that the signed-in user can access that installation (that it merely exists is not enough), then links it in a POST from the confirmation screen. A project is created only from a repository of a linked installation, and `projects.repo_id` is recorded from the API at creation. `user_connections` (the ADR 0003 token pair, per user, sealed as today) replaces `owner_connections` and serves owner-grade writes (#386) for the accounts that user owns. Read tokens are minted per installation as today (ADR 0003 decision 6). | One GitHub App per environment for every customer is how GitHub Apps are meant to be installed; the console already holds the app key; per-account linking is one table and one handshake. | A GitHub App per customer (keys in the Worker per tenant); the customer's PAT (owner-grade, not revocable by us). |
| 5 | **Audit is a table.** `audit_events` (`account_id`, `at`, `actor_kind ∈ user \| job \| runner \| system \| operator`, `actor`, `kind`, `target`, `details` JSON, `ip_country`) is append-only and written in the same batch as the action for: sign-in and sign-out, identity link, invite created/accepted/revoked, role changes, installation linked/unlinked, runner enrolled/revoked, inference key set/rotated/deleted, hosted mode enabled/disabled, spend-cap changes, dispatches and claims, cutover switch and rollback, plan/entitlement changes by the operator. Account owners read it (`GET /api/v1/accounts/:id/audit`, cursor-paged); it is never edited and holds no secret values (the redactor runs on `details`). `item_events` stays the per-item audit. | A customer who pays for an agent team needs to see who gave it which key and which repository; the operator needs the same for incidents. | Logs only (not queryable by the customer, not durable). |
| 6 | **Billing is a seam, not a feature.** `accounts.plan ∈ free \| team` and `accounts.entitlements` JSON (`max_projects`, `max_members`, `hosted_runner: bool`, `max_concurrency`, `spend_cap_usd_month`) are read by one function, `entitlementsOf(account)`, that every limit check calls; the operator sets them through the Access-protected admin route; defaults are the free tier. No payment provider, no invoices, no card data. | The limits must exist for isolation and cost control whatever the pricing turns out to be; the pricing is the owner's later decision. | Stripe now (a paid-side surface before a product). |
| 7 | **Two execution modes per account, both on the same job protocol.** **(a) Self-hosted runner**: the customer installs `team-console-runner` (a release asset verified as decision 8 says; `enrol` by the one-time code of ADR 0006). It runs the **unmodified Claude Code CLI**; the customer signs in on their own machine through Anthropic's flow or configures their own API key in the runner's config; **the console never sees, stores, proxies or copies that credential**: the runner passes a credential *location* (an `ANTHROPIC_API_KEY` from its own config, or the customer's Claude config directory mounted read-only into the job sandbox — the customer's choice, with the residual that an injected job can read the OAuth refresh token in it, RR11), never a value, and never uploads it. **(a′) GitHub Actions packaging** of the same binary (`team-console-runner.yml` in the customer's repository) is the zero-infrastructure form of (a), with these **requirements, not recommendations**: the trigger is **`workflow_dispatch` only** (never `pull_request_target`, `issue_comment`, `workflow_run`); the console dispatches **only on the default branch**, with an app token **downscoped to `repository_ids: [that repo]` and `permissions: {actions: write}`** (adding `actions: write` to the app is an R1-class permission change that needs the owner's approval; the installation-wide permission never backs a wider token); the inference key lives in a **GitHub Environment whose deployment-branch policy allows only the default branch**; the workflow holds **no long-lived console credential** — it requests a **GitHub OIDC token** (`id-token: write`) and the console verifies `iss`, `aud`, `repository_id`, `workflow_ref`, `ref` (the default branch), `run_id` and the job id, then exchanges it for **the job token of that one job** (`jobs.dispatch = 'actions'`, `run_id` recorded, one exchange per job); the **only input is the job id**, validated against the ULID pattern and read through `env:`, never interpolated into `run:`; `permissions: {contents: read, id-token: write}`, `actions/checkout` with `persist-credentials: false`, every action **pinned by commit SHA**, no `actions/cache`, no artifact upload; the CLI stream goes to the console's events (redacted), not to the log, and the log carries only the job id; a job whose work is a **fork PR's head** runs `npm ci --ignore-scripts` (and no tests from that head) or waits for the owner's approval; `::add-mask::` is defence in depth only (a compromised job can encode or send the value — residual Medium, RR11). **(b) Hosted runner**: the console runs the job on infrastructure the operator pays for, using the **customer's own Anthropic API key** (BYOK) stored sealed per account (`inference_keys`, envelope in "Sealing"), released **once, in the claim response, to the machine that presents the job's bootstrap token** — never in the provider's machine config, never in provider secrets, never in D1 plaintext, logs or events (redactor pattern `sk-ant-`); rotated or revoked by the account owner in one screen; spend caps as decision 9. **No mode ever uses a Claude.ai subscription on our servers**, and the hosted dispatcher refuses to start a job whose environment or mounts would carry a Claude OAuth credential. | Anthropic's terms allow exactly these two shapes (the unmodified binary with the end user's own credential; API keys for third-party products); the owner wants no path through our servers on anyone's subscription. One job protocol means the plugin, the matrix and the gate do not know which mode ran the job. | A hosted runner on the customer's subscription (forbidden by the terms and by the owner); the console relaying Claude.ai OAuth (forbidden); a shared operator API key with resale (forbidden: "may not pay for, resell, or intermediate Claude usage"); a runner token or key as a repository secret or a `workflow_dispatch` input (readable by any branch's workflow or public in the run UI). |
| 8 | **Every job runs in its own sandbox; no state crosses jobs or accounts; the runner trusts only what it was installed with.** ADR 0006's L3 (two macOS users) becomes one of **four isolation backends** of the runner: `container` (default where a container runtime exists — Docker, Podman or Apple's container runtime; one fresh container per job from the pinned runner image, the clone as its only writable volume, no access to the runner's config, the socket bind-mounted), `user` (ADR 0006's `_tcrunner`/`_tcjob` layout for a Mac without a container runtime), **`actions-ephemeral`** (the runner *is* a single-job GitHub-hosted VM, proven by the OIDC token of decision 7(a′) — `run_id` and `job_id` match, the VM is discarded by GitHub after the job; allowed for accounts with real projects, including the owner's), and `none` (dev/stage fixture environments only; refused on an account with real projects; refused by the #437 switch). Hosted jobs run **one ephemeral machine or container per job** on the chosen provider (decision 9), created by the console at dispatch with a **one-time bootstrap token** (10 minutes, single use, hashed in `jobs.bootstrap_token_hash`, bound to the job and the dispatch's `hosted_instance_id`); the machine is **deleted** (not stopped — a stopped machine keeps its root filesystem) at `finish` or at `maxMinutes`, and a Cron sweep deletes anything past `maxMinutes + 5`. A hosted runner identity exists **per account** (`runners.hosted = 1`, enrolled by the console when the account enables hosted mode), so a hosted job's token names the account whose key it runs on, and `jobs.account_id` is checked against `inference_keys.account_id` before a key is released. The cross-job controls of ADR 0006 ("Run": fresh `HOME`/`TMPDIR`, read-only managed settings with hooks disabled, hook-type git-config refusal, the plant-then-verify test — run across **two accounts** on the hosted backend) hold inside every backend. **Trust root**: the installed runner carries its verification identity (the Sigstore identity of this repository's release workflow on a `v*` tag, or a pinned public key) **inside the binary it was installed with**; it changes only through a signed release; the console names a release (`GET /api/v1/runner/release`) but the runner **refuses any version lower than the installed one or below a signed minimum**, verifies signature and provenance itself, and the customer may **pin a version or turn auto-update off**. | A per-job sandbox is the multi-tenant form of L3: the owner's Mac was one host for one team; a hosted fleet is many accounts on shared infrastructure, where "no `_tcjob` process survives" is not enough — nothing may survive at all, and nothing from account A may be mounted into account B's job. A trust root the console could change at runtime would make a console compromise code execution on every customer machine. | Shared long-lived workers with a user per account (persistent state, uid management per tenant); Firecracker/VM per job on self-hosted (the container runtime is what customers have); `none` on the owner's Actions VM (the first revision of this ADR; it contradicted the refusal rule and attested nothing); a release key served by the console. |
| 9 | **Hosted provider: Fly Machines first, in one isolated Fly app per account; Cloudflare Containers second. Spend is a reservation, and the hard cap is the customer's.** Both providers are **paid** and need the owner's `/approve` before anything is deployed. **Fly Machines** (`docs.fly.io/about/pricing`, read 2026-11-09): `shared-cpu-2x` with 2 GB is $13.39/month in the cheapest regions, i.e. ≈ $0.0186/hour billed per second while running → **a 90-minute job ≈ $0.03**; a stopped machine bills only its root filesystem at $0.15/GB-month, and a deleted one nothing; no platform fee. **Cloudflare Containers** (`developers.cloudflare.com/containers/pricing/`, read 2026-11-09): included with the **Workers Paid plan ($5/month)**, which includes 25 GiB-hours of memory, 375 vCPU-minutes and 200 GB-hours of disk a month; beyond that $0.0000025 per GiB-second, $0.000020 per vCPU-second, $0.00000007 per GB-second; instance types `basic` (¼ vCPU, 1 GiB) to `standard-4` (4 vCPU, 12 GiB). A 90-minute job on `standard-1` (½ vCPU, 4 GiB) is 6 GiB-hours and ≤ 45 vCPU-minutes — **about four such jobs a month fit inside the included allotment**, and each further one costs ≈ $0.05–0.08. **Isolation on Fly**: **one Fly app per account**, created by the console with its **own isolated private network** (no shared 6PN, no `.internal` discovery across accounts), **no inbound services**, egress through an **allowlist** (the Anthropic API, GitHub, the console API, the package registries the account declares); the Fly API token the Worker holds is **scoped to those runner apps, never an org token** (a C10 asset). `HostedBackend.start(job, bootstrapToken)` receives **no key**; the machine claims with the bootstrap token and receives the key once (decision 7b). **Recommended (H-2 decides with evidence)**: a credential-injecting sidecar in the machine under a separate uid, with the CLI pointed at it through `ANTHROPIC_BASE_URL`, so the job process never holds the key. **Spend**: `payload.maxUsd` is **reserved** in `account_spend` at dispatch (the dispatch is refused when `reserved + spent + maxUsd` exceeds `spend_cap_usd_month`) and **reconciled at `finish`** from the CLI's reported `total_cost_usd`; the per-job budget is also passed to the CLI (`--max-budget-usd`) with `maxMinutes` as the hard kill; because the reported figure comes from inside the sandbox, **the only hard cap is the spend limit the customer sets on their Anthropic workspace**, and hosted mode is enabled for an account only after the owner confirms one exists (residual Medium, RR11). Implementation behind a `HostedBackend` interface (`start`, `destroy`, `status`); Fly first, Containers second; until approved, `entitlements.hosted_runner = false` for every account. | Pay-per-second with no idle cost matches a queue that is empty most of the day; a microVM per job in a per-account network is the strongest isolation on offer at that price. | GitHub Actions on our account as the hosted runner (the Free plan's included compute on private repositories is a monetary allowance — $12/month, `docs.github.com/en/billing/managing-billing-for-your-products/about-billing-for-github-actions`, read 2026-11-09 — and our minutes for customer jobs is intermediation of compute we would have to bill); a free VM (Oracle Always Free) as the fleet (fine for one team, not a product's hosted tier — kept as a self-hosted target); Workers alone (no process, no filesystem); machines of all accounts in one Fly app (shared private network). |

| 12 | **Runner placement is a per-project policy, switchable without re-enrolling.** An account enrols **any number of self-hosted runners** (the same binary; e.g. the owner's Mac with backend `user` and a VPS he owns with backend `container`), each with a `name` and `allowed_projects`. **`projects.runner_policy`** (JSON, falling back to **`accounts.default_runner_policy`**) says which may claim the project's jobs: `{ "mode": "pinned", "runner": "<id>" }` (one runner — "local" or "cloud"), `{ "mode": "any" }` (every allowed runner of the account), or `{ "mode": "failover", "preferred": "<id>", "fallback": ["<id>…"], "offline_after_seconds": 300 }` (the preferred runner while it heartbeats; when `last_seen_at` is older than the threshold, the fallbacks may claim; a job already claimed stays with its runner). The hosted runner (decision 9) is one more entry in the same policy once hosted mode is enabled, so "local → cloud" is a switch, not a migration. **Why Anthropic's own cloud (Claude Code on the web, routines) is not a runner host for us today**: the late-October failures ("organization has disabled Claude subscription access for Claude Code") took every cloud routine down without notice, and the cloud's egress proxy rewrites GitHub authentication so the bot and role identities this architecture rests on cannot sign there (ADR 0006 "Context"; memory of the 2026-11-03 pause) — a host where our identities cannot hold is not a runner. **Why our hosted runner never takes a personal subscription**: a subscription credential on a machine we operate would be *us* routing requests through Pro/Max credentials on a user's behalf — exactly what Anthropic's terms forbid (Context) — whatever the customer consents to; the owner's subscription therefore runs only on hosts he owns (`user`/`container`), and the hosted runner only on API keys (decision 7b). **Owner money decision**: a VPS for the `container` runner is the owner's own spend (a small instance is a few euros a month; nothing is needed from us); the team sets nothing up until he says so. | The owner wants to move his team between his Mac and a machine of his own without ceremony, and later to our hosted tier; a policy over enrolled runners is one column and one `WHERE` clause, and the same mechanism gives customers failover between their own runners. | A single active runner per account (re-enrol to move); "move" as revoke + enrol (loses `allowed_projects`, keys and history); routing by job kind only (the owner wants it per project). |

### Sealing (inference keys)

AES-256-GCM with a **random 96-bit IV per seal**; the data key is HKDF-derived from a **separate Worker secret,
`INFERENCE_KEY_ENCRYPTION_KEY`** (not `TOKEN_ENCRYPTION_KEY`, so GitHub token pairs and inference keys rotate
independently with separate blast radius), `info = 'inference-key:v<root_key_version>'`; AAD is
`account:<id>:anthropic:<key_id>` so a ciphertext cannot be moved between accounts or put back after a rotation;
`root_key_version` is stored beside the ciphertext so the root secret can be rotated (re-seal on next use, refuse
an unknown version). The scheme reuses `libs/worker/core/src/lib/sealed.ts` with these parameters.

## Identity, routes and the matrix

- `authMiddleware` mints `user` from the `__Host-tc_session` cookie (the Access path remains for the owner until
  decision 3's cutover and for `/api/v1/admin/*`), `service` as today on dev/stage, `runner` and `job` per ADR 0006
  decision 8 and the #446 note (opaque job token + the claiming runner's identity; `actions`: the OIDC exchange;
  `hosted`: the bootstrap token claims, then the job token). `identity.kind = 'user'` carries `userId` and
  `memberships: {accountId, role}[]`.
- **Customer runner authentication without Access** (reconciles ADR 0006 decision 8): a self-hosted runner reaches
  `/api/v1/runner/*` over HTTPS with its **EdDSA runner JWT alone** (`exp` ≤ 5 min, `jti` replay refused, `aud` =
  the environment), revoked by `runners.revoked_at`, rate-limited per runner id and per IP by the Worker (D1
  counters) and by a Cloudflare WAF rate-limiting rule on `/api/v1/runner/enrol`; the Access service-token pair of
  ADR 0006 stays **optional** — required on dev/stage (the team's perimeter) and offered to customers who front
  their own runner with Access, never required of them. The job's proxied calls carry the runner JWT and the job
  token as before (R4). The hosted and Actions machines authenticate the same way after their one-time bootstrap or
  OIDC exchange.
- `accountAccess` resolves the **scope** (decision 2); `projects/lookup.ts` takes it and answers 404 outside it.
  `trackerAccess` runs after it; the `owner` policy actor is "a user with `role = owner` in the project's
  account"; a `member` is a new policy actor with reads, `comment`s, `proposed` item creation and `requests` —
  never decisions, asks' answers, approvals, sprints, labels or settings.
- Account routes (`/api/v1/accounts/:id/{members,invites,installations,runners,inference-key,audit,settings}`)
  are owner-of-account only, with the same CSRF rules as every cookie-borne write; `POST /api/v1/accounts` is any
  signed-in user (self-service, rate-limited per user and per IP); `/api/v1/admin/*` is the operator (Access JWT
  verified by the Worker + allowlist).
- The **route inventory spec** (decision 2) is the acceptance test of every route added from here on.

## Runner, installer and hosted dispatch

- **Installer** (self-hosted): `curl -fsSL … | sh` is refused as a pattern — the documented path is a **release
  asset verified before it runs**: `team-console-runner-<version>-<os>-<arch>.tar.gz` with **Sigstore keyless
  signatures and GitHub artifact attestations** (`actions/attest-build-provenance`, free on public repositories)
  produced by a **separate, minimal release workflow** (`release-runner.yml`, `permissions: {contents: write,
  id-token: write, attestations: write}`, no deploy secrets) on a **`v*` tag protected by a tag ruleset**; container
  images signed with **cosign** and referenced by digest; a Homebrew tap formula pinned to the checksum in a tap
  repository with the same ruleset and attestation checks. The installer verifies signature and provenance against
  the pinned identity of this repository's release workflow, creates the runner's directories (and, for the `user`
  backend, the two local users with the documented single sudoers rule), writes the config, runs `enrol`, and never
  writes outside its prefix.
- **Self-update** follows decision 8: trust root in the installed binary, no downgrade, customer pin or opt-out.
- **Backends** (decision 8) are chosen at `enrol` (or implied: `actions-ephemeral` by the OIDC exchange, hosted by
  the dispatcher) and reported in `capabilities`; the console refuses to enqueue a job of an account with real
  projects onto a runner whose backend is `none`.
- **Credentials inside a job**: mode (a) — `ANTHROPIC_API_KEY` from the runner's config, or the customer's Claude
  config directory mounted read-only (the runner never opens the files; RR11 states the exposure); mode (a′) — the
  key from the branch-restricted GitHub Environment; mode (b) — released once in the claim response (decision 7b),
  held by the sidecar where H-2 confirms it. The runner and the console refuse to start a hosted job whose
  environment would carry a Claude.ai OAuth credential. Per-role model (`roles.<role>.model`) and the usage budget
  of the #446 note (concurrency, back-off on rate-limit or usage-limit output, visible in the console) hold in every
  mode; `--max-budget-usd` is passed in hosted mode.
- **Hosted dispatch**: `POST …/jobs` (Run now, a schedule or a webhook) → if the account is hosted and the job's
  kind is not `needs_local`, the Worker reserves `maxUsd`, mints the bootstrap token, calls `HostedBackend.start`
  with the runner image, `TC_API_URL` and the bootstrap token **only**, and records `hosted_instance_id`; the
  machine claims with the bootstrap token, receives the job token and the key once, runs `run-once`, finishes, and
  the Worker **deletes** it (also from a Cron sweep for anything past `maxMinutes + 5`), then reconciles spend.
- **Actions dispatch**: the Worker mints the downscoped dispatch token and calls `workflow_dispatch` on the default
  branch with `inputs: {job_id}`; the run exchanges its OIDC token for the job token (decision 7a′).
